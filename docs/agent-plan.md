# 桌宠 Agent 接入方案

## 建议范围

第一阶段做“自然语言指挥 + 自动排班 + 角色对话”。玩家可以说“留一只扫地，另一只灭虫，累了就换班”。Agent 根据生态快照选择桌宠与任务，再通过游戏命令接口执行。

现有 `Simulation` 已经负责自主寻路、攻击、清洁、体力和技能，继续作为权威规则。Agent 不负责每帧移动、不直接改存档、不模拟系统鼠标点击。单个规划 Agent 管理整个小队，六只桌宠使用不同的性格设定；首版无需六个并行模型。

## 架构

```text
控制台 / 悬浮栏聊天入口
        |
        v
AgentCoordinator（异步请求、超时、取消、去重）
        |                     |
        v                     v
只读 GameSnapshot        IAgentProvider
                          本地模型 / 自有服务
                               |
                               v
                         结构化计划或工具调用
                               |
                               v
CommandGateway（版本校验、命令白名单、规则校验）
                               |
                               v
WPF Dispatcher -> Simulation -> 既有动画与桌宠行为
```

`IAgentProvider` 隔离模型服务差异。当前 .NET Framework 4.8 客户端可通过 HTTPS 和 JSON 调用服务，无需为了接入 Agent 先重写应用。网络请求必须在 UI 线程之外；结果切回 Dispatcher 执行。

## 给 Agent 看什么

快照包括快照序号、游戏时间、暂停状态、蟑螂/幼虫/卵鞘/污渍数量、污染度、六只桌宠的体力和技能、当前任务、冷却、派遣名额，以及玩家本次指令。

首版只传游戏内部状态，不需要桌面截图、窗口标题、文件列表或用户在其他软件中的内容。生态本来就在内存中，无需视觉识别。角色长期记忆只保留玩家自选称呼、语气偏好和游戏内互动摘要。

## 命令接口

| 命令 | 参数 | 执行条件 |
| --- | --- | --- |
| `get_game_state` | 无 | 返回只读快照 |
| `assign_pet` | `petId`, `job` | 有派遣名额，体力满足现有规则 |
| `recall_pet` | `petId` | 目标已经派出 |
| `say` | `petId`, `text` | 字数和频率限制，显示游戏气泡 |
| `suggest_care` | `petId`, `reason` | 提示主人喂食、照顾或陪伴 |

喂食和陪伴首版保留给主人，Agent 可以提醒，避免自动饲养消除照顾玩法。需要自动饲养时再增加独立选项与对应命令。所有动作调用现有 `DispatchPet`、`RecallPet` 等方法，禁止把模型返回值当代码执行。

示例模型输出：

```json
{
  "snapshotRevision": 128,
  "actions": [
    { "type": "assign_pet", "petId": 2, "job": "clean" },
    { "type": "assign_pet", "petId": 5, "job": "hunt" }
  ],
  "reply": "充鹅不闻负责清扫，等放假鹅负责远程灭虫。"
}
```

输出需经 JSON Schema 或等价结构校验。命令必须重新检查最新状态；过期计划丢弃，派遣失败返回明确结果。一个计划内的依赖动作按顺序执行，遇到失败停止后续依赖动作。请求 ID 防止重试重复执行。

## 什么时候调用

- 用户发送自然语言指令时立即请求。
- 自动模式开启后，污染越过阈值、桌宠耗尽、任务完成时触发重新规划。
- 合并短时间连续事件，自动请求最多每 15 至 30 秒一次。
- 每次仅一个规划请求在途，新的玩家指令取消旧规划。
- 玩家手动调整某只桌宠后，短期锁定该任务，避免 Agent 立即改回。
- 玩家暂停、锁屏、退出桌面入侵时取消待执行动作。

网络失败或超过约 8 秒未响应时保持原任务运行。连续失败进入短暂退避；界面显示连接状态。离线默认规则可优先清理即将孵化的卵鞘，再按污染度选择清扫或灭虫。

## 部署选择

| 方案 | 适合情况 | 代价 |
| --- | --- | --- |
| 本地模型服务 | 个人原型、离线体验 | 用户需另装推理运行时并下载模型，硬件有要求 |
| 玩家自行配置 API | 小范围技术用户测试 | 配置步骤增加，费用由玩家承担；密钥用 Windows DPAPI 加密保存 |
| 自有服务代理模型 | 面向普通玩家分发 | 你承担服务部署、账号、配额和调用成本 |

建议先做可替换 Provider 的开发原型，默认 Agent 关闭；产品化再接自有服务。不要把供应商密钥写入 exe 或便携包。代理服务保存密钥，客户端持短期凭证，服务按用户限流、限制响应长度和预算。

## 实施顺序

1. 提取 GameSnapshot 与 CommandGateway，用本地假 Provider 验证自然语言入口以外的全流程。
2. 增加悬浮栏聊天气泡与 Agent 开关，接通一个 Provider，实现手动指挥。
3. 加入事件驱动的自动排班、玩家手动任务保护和失败回退。
4. 添加角色语气与少量记忆，最后评估语音，不影响主游戏启动与帧率。

验收重点：暂停期间不执行旧计划、重复请求不重复动作、没有第三个派遣名额、零体力技能规则保持正确、断网不冻结界面、玩家手动命令优先、模型输出未知命令时拒绝执行。

本轮仅提供方案，尚未接入模型服务、上传游戏状态或添加外部依赖。
